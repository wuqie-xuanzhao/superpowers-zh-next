# BDD 最佳实践

## 1. 核心生命周期：讨论、编写、自动化

现代 BDD（2024+）强调：BDD 首先是关于**对话**，其次才是自动化。

### 讨论（三 Amigo）

在写代码或测试之前，产品、开发、测试三方讨论功能。

- **目标：** 达成共识
- **方法：** 结构化对话，常用 **Example Mapping** 技术
- **产出：** 系统应该如何行为的具体示例

### 编写（Gherkin）

把讨论出的示例转化为 Gherkin 格式的结构化场景。

- **目标：** 可执行的规格 / 活文档
- **标准：** 写**声明式**场景，描述业务行为而非 UI 实现细节
- **参考：** 详见 `gherkin-guide.md`

### 自动化（TDD + 红-绿-重构）

用红-绿-重构循环实现场景。

## 2. 红-绿-重构循环

这是实现的引擎。

### 🔴 红灯：写一个失败的测试

- **规则：** 没有失败的测试，就不写生产代码
- **验证：** 运行测试，它必须失败。如果通过了，要么测试有问题，要么功能已存在
- **最佳实践：** 写小的、聚焦的测试，一次只测一个行为

### 🟢 绿灯：让它通过

- **目标：** 写**最少**的代码让测试通过
- **心态：** "让它能跑。" 不要优化，不要过度设计
- **YAGNI：** 不要添加当前测试不要求的字段或逻辑

### 🔵 重构：让它干净

- **目标：** 在不改变行为的前提下改善代码结构
- **安全网：** 绿灯测试确保重构不会破坏功能
- **动作：** 消除重复、改善命名、提取方法、应用设计模式

## 3. 通用最佳实践

- **测试左移：** 测试发生在开发过程中，而非之后
- **活文档：** .feature 文件应该让业务干系人能读懂，并作为需求真相来源
- **一个场景一个行为：** 保持场景聚焦
- **CI/CD 集成：** 在流水线中运行 BDD 场景
- **测行为不测实现：** 测试应该能经受重构。如果重命名一个私有变量就破坏了测试，说明测试与实现耦合过紧

## 4. BDD vs TDD

| 维度 | TDD | BDD |
|------|-----|-----|
| 视角 | 开发者（单元测试） | 用户（验收测试） |
| 回答的问题 | 代码实现是否正确？ | 系统行为是否符合需求？ |
| 粒度 | 函数/方法级 | 功能/场景级 |
| 最好搭配 | 与 BDD 结合使用 | 用 BDD 定义做什么，TDD 验证怎么做 |

## 5. 常见错误

| 错误 | 修正 |
|------|------|
| 场景描述 UI 操作步骤 | 改为描述用户意图 |
| 一个场景测试多个规则 | 拆分为独立场景 |
| 场景依赖其他场景结果 | 每个场景自包含前置条件 |
| 只有开发人员编写场景 | 邀请产品和测试参与讨论 |
| 跳过讨论直接写场景 | 先 Example Mapping，再写场景 |
| 场景实现后不维护 | 场景是活文档，需求变时同步更新 |
