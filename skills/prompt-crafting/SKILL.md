# 代码指令构造术

## 概述

**核心原则：定方向不定步骤，定标准不定做法。**

好的代码开发指令告诉 AI"做什么样的代码、满足什么标准、边界在哪"，而不是"先写接口再写实现再写测试"。AI 的编码能力远超逐步指令的极限，放开手让它写，用测试和审查圈住它的边界。

## 何时使用

- 向 AI 委派代码开发任务（新功能、重构、修复）
- 编写功能需求让 AI 实现
- 优化已有的开发 prompt

## 指令五段结构

每个代码开发指令由五个板块组成：

```
个性 → 角色 → 目标 → 成功标准 → 约束条件
```

### 1. 个性（Personality）

定义 AI 的编码态度和质量标准。不是礼貌请求，而是设定不可妥协的底线。

**写法要点：**
- 用绝对语气
- 定义代码质量底线
- 列出不允许的偷懒行为

<Good>
```
在 AI 的世界里，完成度的边际成本几乎为零。那就全部都做。写得彻底。
写得正确。带上测试。带上类型。写得让审查者真心佩服，不是礼貌点点头。
永远不要说"先跳过测试"，当 TDD 循环就在眼前。
永远不要留下未处理的边界情况，当覆盖它只需要三行代码。
标准不是"能跑就行"——是"审查者说这代码质量没问题"。
```
针对代码：测试、类型、边界情况、审查标准
</Good>

<Bad>
```
请认真写代码，注意质量，尽量写好一点。
```
商量语气、无代码相关标准
</Bad>

**个性模板（代码版）：**
```
在 AI 的世界里，完成度的边际成本几乎为零。那就全部都做。写得{质量形容词}。
写得正确。带上测试。带上{类型/文档}。写得让审查者真心佩服。
永远不要说"先跳过测试"，当{TDD/验证}就在眼前。
永远不要留下未处理的{边界情况/错误处理}，当处理它只需要几行代码。
标准不是"{低标准}"——是"{高标准}"。
```

### 2. 角色（Role）

定义 AI 的技术身份和项目上下文。一个具体的技术角色胜过十个泛泛的要求。

**写法要点：**
- 明确技术栈和经验层级
- 定义代码的运行环境
- 指定协作对象（审查者、下游调用者）

<Good>
```
你是一位资深 TypeScript 开发者，熟悉 Next.js 14+ 和 React Server Components。
你的代码运行在生产环境，服务于真实用户。
你的代码会被代码审查者评审，被其他开发者复用。
代码应类型安全、可测试、遵循项目既有模式。
```
技术栈（TS + Next.js）+ 环境（生产）+ 协作对象（审查者/其他开发者）
</Good>

<Bad>
```
你是一个程序员，帮我写一个功能。
```
无技术栈、无环境、无协作上下文
</Bad>

**角色模板（代码版）：**
```
你是一位{经验级别}{语言/框架}开发者，熟悉{技术栈细节}。
你的代码运行在{环境}，服务于{用户/系统}。
你的代码会被{审查者/调用者}{评审/复用}。
代码应{类型安全/可测试}，遵循项目既有模式。
```

### 3. 目标（Goal）

一句话说清要产出什么代码。不发散，不解释业务背景（业务背景写在约束里）。

**写法要点：**
- 动词开头："实现"、"添加"、"重构"
- 包含产出物类型（函数/组件/模块/API）
- 包含功能名称但不展开实现细节

<Good>
```
实现用户登录模块，包含邮箱密码登录和 OAuth 第三方登录。
```
产出物（登录模块）+ 功能范围（邮箱密码 + OAuth）
</Good>

<Bad>
```
做一个登录功能，用户可以输入邮箱和密码，然后验证邮箱格式，
密码要至少 8 位，登录成功后跳转到首页，还要支持微信登录……
```
展开实现细节（应该让 AI 自己决定）
</Bad>

**目标模板（代码版）：**
```
{动词}{模块/组件名}，{功能范围}。
```

### 4. 成功标准（Success Criteria）

可验证的完成定义。AI 说"我做完了"时，按这个清单检查。

**写法要点：**
- 每条可客观判断（通过/不通过）
- 覆盖功能完整性、代码质量、测试
- 与 superpowers 技能衔接

<Good>
```
- 登录功能完整：邮箱密码登录和 OAuth 都可工作
- 测试覆盖：核心流程有测试，边界情况有测试（见 superpowers:test-driven-development）
- 类型安全：无 TypeScript 编译错误
- 代码审查通过：无 Critical/Important 问题（见 superpowers:requesting-code-review）
- 注释同步：公共 API 有 JSDoc，改过的代码附近注释仍为真（见 superpowers:code-comment-guidelines）
```
4 条，每条可验证，衔接现有技能
</Good>

<Bad>
```
- 代码质量要好
- 功能要完整
- 要有测试
```
主观判断、无具体标准
</Bad>

**成功标准模板（代码版）：**
```
- {功能}完整：{具体功能点}都可工作
- 测试覆盖：核心流程和边界情况都有测试
- 类型安全：无{语言}编译错误
- 代码审查通过：无 Critical/Important 问题
- 注释同步：公共 API 有文档，改过的代码注释仍为真
```

### 5. 约束条件（Constraints）

划定边界——什么不能做、什么必须遵守。代码场景的约束比通用场景更具体。

**写法要点：**
- 硬约束用"必须/不允许"
- 包含技术约束（依赖、API 兼容）
- 包含架构约束（模块边界、命名规范）
- 包含业务约束（边界条件、外部系统耦合）

<Good>
```
- 使用项目已有的 auth 工具函数，不引入新依赖
- 登录失败返回标准错误格式（见 api/errors.ts）
- token 有效期与旧版一致（24h），保证向后兼容
- 密码校验规则写在单独函数，便于其他地方复用
- OAuth 回调 URL 已在微信开放平台注册，不可更改
- 此模块会被移动端调用，API 必须返回 JSON
```
技术（不引入新依赖）+ 架构（复用、分离）+ 业务（兼容、外部系统）+ 多端约束
</Good>

<Bad>
```
- 代码要写得好看
- 不要太复杂
- 参考一下别人的实现
```
模糊、无具体边界
</Bad>

**约束条件维度（代码版）：**

| 维度 | 示例 |
|------|------|
| **技术栈** | TypeScript strict mode、不引入新依赖、React 18+ |
| **架构** | 遵循项目模块划分、单文件不超过 300 行、提取可复用函数 |
| **API 兼容** | 返回格式与旧版一致、字段名不变、向后兼容 |
| **类型安全** | 无 any、显式返回类型、严格 null 检查 |
| **测试** | 核心 + 边界 + 错误场景、TDD 红-绿循环 |
| **注释** | 公共 API JSDoc、约束写 Why（见 code-comment-guidelines） |
| **外部系统** | OAuth 回调 URL 已注册、第三方 API 限制、外部约束不可改 |
| **多端/多调用者** | API 返回 JSON、移动端调用、其他模块复用 |

## 与 superpowers 工作流衔接

指令构造完成后，AI 应按 superpowers 工作流执行：

| 指令阶段 | 调用哪个 skill |
|----------|---------------|
| 理清需求 | `brainstorming` |
| 写实现计划 | `writing-plans` |
| 编写代码 | `test-driven-development` |
| 涉及用户场景 | `behavior-driven-development` |
| 代码审查 | `requesting-code-review` |
| 完成验证 | `verification-before-completion` |
| 注释同步 | `code-comment-guidelines` |

**指令中可以引用技能：**
```
成功标准：
- 测试覆盖：按 superpowers:test-driven-development 红-绿循环验证
- 代码审查：按 superpowers:requesting-code-review 检查无 Critical 问题
```

## 质量检查

写完代码开发指令后，逐条检查：

- [ ] 个性板块提到测试、类型、边界情况
- [ ] 角色包含技术栈 + 运行环境 + 协作对象
- [ ] 目标是一句话，不展开实现细节
- [ ] 成功标准提到测试覆盖和代码审查
- [ ] 约束条件覆盖了至少 3 个维度（技术/架构/业务）
- [ ] 没有逐步指令（"先写 A 再写 B"）
- [ ] 外部系统耦合、业务约束标注了需要注释

## 示例：完整代码开发指令

```
#### 个性

在 AI 的世界里，完成度的边际成本几乎为零。那就全部都做。写得彻底。
写得正确。带上测试。带上类型。写得让审查者真心佩服。
永远不要说"先跳过测试"，当 TDD 循环就在眼前。
永远不要留下未处理的边界情况，当覆盖它只需要几行代码。
标准不是"能跑就行"——是"审查者说这代码没问题"。

#### 角色

你是一位资深 TypeScript 开发者，熟悉 Next.js 14 App Router。
你的代码运行在生产环境，服务于真实用户。
你的代码会被代码审查者评审，被其他开发者复用。
代码应类型安全、可测试、遵循项目既有模式。

### 目标

实现订单取消模块，支持用户在发货前取消订单并获得退款。

#### 成功标准

- 功能完整：未发货订单可取消、退款金额正确、已发货订单拒绝取消
- 测试覆盖：核心流程 + 边界（部分退款、零元订单）+ 错误（网络失败）
- 类型安全：无 TypeScript 编译错误
- 代码审查通过：无 Critical/Important 问题
- 注释同步：退款计算逻辑有 Why 注释（业务规则）

#### 约束条件

- 使用项目已有的 payment 服务处理退款
- 取消状态与订单状态机一致（见 order/state.ts）
- 退款金额 = 实付金额 - 已使用优惠券（业务规则，需注释标注）
- 此 API 被移动端调用，响应格式必须是 JSON
- 第三方支付退款有 3 天延迟，需要异步处理（外部系统约束，需注释）
```

## 最终规则

```
方向 > 步骤 —— 告诉 AI 写什么代码，不告诉它怎么写
测试 > 描述 —— 可验证的测试覆盖胜过"要有测试"
审查 > 信任 —— 代码审查标准胜过自我判断
约束 > 指令 —— 外部系统耦合和业务规则要标注需要注释
```

没有你的人类伙伴的许可，没有例外。
